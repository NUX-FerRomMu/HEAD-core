# Git and review contract

Use the Git executable through argument arrays and explicit working directories; never concatenate shell commands. Pin/document the minimum tested Git version during bootstrap. Validate branch refs using Git and reject paths escaping the worktree; support spaces, Unicode and rename metadata. Full SHA-1 or SHA-256 object IDs are opaque strings. Do not assume 40 characters.

## Development ownership

Create `<data>/worktrees/<project-id>/<ticket-id>/dev` from the current target base. Default branch template `{kind}/ade-{ticket_id}-{slug}`, with kind map `implementation=feat`, correction profile=`fix`, documentation profile=`doc`. Ticket ID is UUID; slug is sanitized and bounded. Validate custom templates and final refs; branch collision is a visible conflict, never automatic reuse/deletion. Persist intended worktree/branch/base in a job before creation; reconcile partial creation on retry. MVP rejects bare repositories, unborn branches, submodules, and Git LFS-managed files with explicit `UNSUPPORTED` and guidance. Do not claim these configurations work without tests.

One fenced development lease controls agent or human writes. Before granting a human lease, pause the developer, wait for its process tree to exit, reconcile worktree HEAD, then increment fence and grant. Before returning to the developer, require clean tracked/untracked state or a human commit/discard decision. Never discard changes automatically. A read-only snapshot/diff of any candidate remains available during writes. ADE clients open snapshot buffers read-only while the developer owns the lease; arbitrary external editors remain outside this enforcement boundary.

Manual-only implementation is supported: acquiring a human writer on a ready ticket checks dependencies, creates the same isolated workspace and moves it to doing without assigning a provider. Acquiring a writer on a committed ticket moves it to fixing and revokes approval before edits. Assigned tickets must first start their assigned workflow or be explicitly cancelled/replaced; writer acquisition cannot silently skip an assignment's initial setup. After editing, commit, release, publish, explicitly record/run validation, then review/approve through the ordinary gates. A human can finish this path with no agent process at all.

Agents may create commits on their ticket branch. `candidate.publish` waits for process exit/release, verifies expected worktree/branch, a clean status including untracked files, new head, and ancestry from recorded base. Its fence must match the latest cleanly released writer lease, with no successor lease granted; use a short publication reservation to prevent a new writer during Git verification and candidate persistence. Capture candidate head/base atomically in the domain after Git checks. Recheck observed HEAD before persisting; uncertain changes produce BUSY/attention. Human commits use the developer worktree only under a human lease, ordinary configured Git author identity, and an audit record identifying the human operation. No fake author identities. Publishing a manual commit follows exactly the same validation/review path.

## Validation isolation

Create a detached validation worktree at the exact candidate head. Store the expected tree hash before and after checks. Test-created ignored outputs are allowed; tracked modifications and untracked source changes make validation `error` with a dirty-checkout reason. Testing agents can propose test patches as artifacts, not modify the certified source. A proposed patch is accepted through the developer/human lease and a fresh candidate. No validation executes in the target/main worktree.

## Review anchors

Diff is `base_sha..head_sha`, with no moving branch refs. Return changed path, old path for rename, status, binary flag, added/deleted counts and structured hunks. `snapshot.read` reads Git objects at the bound side, not a live worktree. Refuse traversal, absolute paths, symlink escapes and blobs over configured limits; large/binary diffs show metadata and an artifact reference when appropriate. Comments retain candidate, side, path and line; on a new candidate mark old open comments obsolete with links to the old snapshot. An open forced correction is carried as an unresolved obligation onto the successor candidate until the human resolves it. Never silently map lines or consider an agent answer resolution.

Review may focus on selected files, but approval always covers the whole candidate. There is no partial-file merge. Editing uses a human writer lease and the live development worktree; the UI clearly distinguishes snapshot buffers from editable buffers.

## Integration algorithm

1. `review.approve` verifies current candidate, passing exact validation/config, no open forced obligations, no development writer, and target SHA equal to candidate base. Store approval and integration job together.
2. Worker acquires the repository integration lease, reloads approval and rechecks every guard. Persist journal `running` with expected target and candidate before Git mutation. Check candidate descends from base and validation remains eligible.
3. Create/check a detached integration staging worktree and verify the candidate. If target is not checked out in any worktree, use `git update-ref <target> <candidate> <expected-base>` for compare-and-swap. If target is checked out, allow only one clean worktree with no ADE writer; verify its HEAD/base and run `git merge --ff-only <candidate>` there. Git's own ref locking/CAS plus post-verification protect against ref races. If any worktree is dirty, target ownership is uncertain, or another external process changes state, stop and ask for intervention; never reset or force checkout.
4. Verify target now equals candidate, persist integration success and ticket done, close the developer, release leases, resolve obsolete attention. Never push remotely. External Git changes are outside ADE's locking; postconditions detect them and may leave the journal `unknown` for reconciliation rather than pretending atomicity across Git and SQLite.
5. On restart: if target equals recorded candidate, finish the recorded integration once. If it equals expected base, retry guarded operation. Otherwise mark blocked/unknown with observed refs; never overwrite the ref or infer success merely because candidate is an ancestor of a later external commit.

If target moved before integration, set integration blocked, revoke approval and enqueue target-update activity. `candidate.refresh_base` moves the ticket to fixing and stores the observed current target as the intended base for the next candidate, without rewriting the old candidate. The assigned developer or human updates the branch against that intended base, resolves conflicts, and publishes a candidate descending from it. If the target moves again, validation may run for that immutable pair but approval remains blocked until another refresh. Failed rebases preserve files and generate intervention. Test and review again. No automatic rebase/merge commit after approval.

Cleanup is explicit after done/cancelled, checks no active process/lease and no dirty changes, and may delete only ADE-owned temporary worktrees. Preserve candidate objects via owned refs until the user opts into history cleanup. Do not delete user branches or worktrees discovered outside ADE ownership.
